# Эксплуатация Bar Exchange Backend

## Ежедневный контроль

1. `GET /health` — статус API и БД.
2. `GET /api/v1/admin/diagnostics` (или страница `/admin`) — состояние iiko, текущий и следующий
   раунд, количество биржевых товаров, режим публикации, статус Telegram и плагина.
3. `GET /api/v1/public/prices` — то, что реально видит фронтенд.

## Регламент раунда

```
cron (каждые 15 мин) → SIMULATED → approve → publish → публичные цены
```

- Симуляция: `POST /api/v1/admin/rounds/simulate` (идемпотентна по `roundKey`).
- Согласование: `POST /api/v1/admin/rounds/:id/approve`.
- Публикация: `POST /api/v1/admin/rounds/:id/publish` — фиксирует `publishedPrice` в БД.
- Откат: `POST /api/v1/admin/rounds/:id/rollback` — возвращает предыдущий опубликованный раунд.
- Ручной перенос в iiko: `GET /api/v1/admin/rounds/:id/manual-export`.

Публикация в v0.1 **не меняет цену в кассе**. Если цену нужно изменить в iiko — используйте
ручной экспорт и штатные инструменты iiko.

## Типовые инциденты

| Симптом                                | Действия                                                                                                                     |
| -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| Фронтенд показывает старые/пустые цены | Проверить `public/prices` → есть ли `PUBLISHED` раунд на текущее окно; при необходимости симулировать и опубликовать вручную |
| Cron не создаёт раунды                 | Логи Cron-сервиса Railway, `iiko_sync_attempts`, Telegram-алерты                                                             |
| `IIKO_*` ошибки                        | См. [IIKO_SETUP.md](IIKO_SETUP.md), раздел диагностики                                                                       |
| 401 на админ-эндпоинтах                | Совпадает ли `ADMIN_API_KEY` и имя заголовка `ADMIN_API_KEY_HEADER`                                                          |
| 429                                    | Rate-limit; уменьшить частоту опроса фронтенда/плагина                                                                       |
| Ошибки БД при старте                   | `DATABASE_URL`, доступность Postgres, применены ли миграции                                                                  |
| Дубли событий продаж                   | Ожидаемо: webhook идемпотентен, ответ содержит `duplicate: true`                                                             |

## Восстановление

**Плохая цена опубликована.** `rollback` нужного раунда → предыдущий опубликованный раунд снова
активен → при необходимости скорректировать `minPrice`/`maxPrice`/`priceStep` товара через
`PATCH /api/v1/admin/products/:id` и заново симулировать.

**Некорректная номенклатура.** Повторный `sync-menu`; исчезнувшие товары архивируются
автоматически, вручную удалять записи не нужно.

**Полная остановка изменения цен.** Отключить Cron-сервис в Railway; публичное API продолжит
отдавать последний опубликованный раунд до конца его окна.

**Отключение интеграции с iiko.** `IIKO_SYNC_ENABLED=false` — backend продолжает работать
на данных из БД.

## Обслуживание

- Миграции применяются автоматически (`db:migrate:deploy` в start-команде).
- Резервные копии: используйте бэкапы Postgres-плагина Railway.
- Рост данных: `audit_logs`, `iiko_sync_attempts`, `sales_events` растут постоянно —
  предусмотрите периодическую архивацию/очистку старше 90 дней.
- Ротация секретов: смените значение в Railway Variables и перезапустите сервис;
  `ADMIN_API_KEY` и `FRONT_PLUGIN_SHARED_SECRET` меняются независимо.

## Что нельзя делать (границы v0.1)

- Включать любые записи в iiko (их нет в коде и не должно появляться без отдельного решения).
- Передавать `ADMIN_API_KEY` на фронтенд или в плагин.
- Включать `IIKO_DEBUG_RAW_PAYLOADS=true` в production надолго.
- Запускать `prisma migrate dev` против production-базы.
